# 按阶段发布的版本管理机制设计

## 1. 目标与边界

本机制为 RACS 建立阶段版本规划、唯一项目版本号来源、变更日志、任务报告和正式发布门禁。

本次只建立发布管理与文档机制，不实现业务功能，不修改架构或产品范围，不创建正式版本、Git 标签或远程 Release，也不把任务规划、测试目标或缺失的 Reviewer 结论写成实际结果。

## 2. 项目版本号

`pyproject.toml` 的 `[project].version` 是项目唯一版本号来源。当前值保持为 `0.1.0`。

- `web/package.json` 是私有前端包配置，不保留独立项目版本号。
- 文档、Git 标签和 Release 名称只引用唯一版本源，不成为新的版本源。
- FastAPI 应用元数据中现有的硬编码版本与唯一版本源重复。由于本任务不修改业务代码，本次只把它登记为一致性风险，交由后续工程任务消除。
- `data/manifest.json` 中的 `dataset_version`、政策版本、规则版本、Prompt 版本和工作流版本是各自制品的独立版本，不等于项目版本。

## 3. 阶段版本规划

以下均为规划目标，不代表任务完成、Reviewer 通过或版本已发布：

| 计划版本 | 任务范围 | 阶段目标 |
| --- | --- | --- |
| `v0.1.0` | T-000 | 工程基线 |
| `v0.2.0` | T-001～T-002 | 产品基线 |
| `v0.3.0` | T-101～T-104 | 基础业务能力 |
| `v0.4.0` | T-201～T-203 | AI 售后流程 |
| `v0.5.0` | T-301～T-304 | 人工协作与恢复 |
| `v1.0.0` | T-401～T-404 | 完整 MVP |

任务范围全部完成仅满足候选条件；正式发布仍必须通过对应阶段 Reviewer 审查和发布检查。

## 4. 文档组成

### `docs/CHANGELOG.md`

采用 Keep a Changelog 风格的简化结构：

- `Unreleased` 只记录已完成且有证据、但尚未正式发布的变化。
- 已发布版本必须记录版本号、发布日期和可验证变更。
- 规划内容不进入已发布版本条目。
- 当前没有足够证据证明任何正式版本已发布，因此初始文件不创建虚构的已发布版本。

### `docs/RELEASES.md`

记录唯一版本源、阶段版本规划、发布门禁、版本提升步骤和一致性检查规则。该文件描述机制和规划，不充当发布结果记录。

### `docs/task-reports/README.md`

定义每个 `T-xxx.md` 报告的命名和必填字段：

- 任务与目标；
- 状态；
- 实际修改；
- 验证命令与实际结果；
- Reviewer 结论及证据；
- 已知限制与未覆盖风险；
- 所属计划版本；
- 发布资格判断。

没有 Reviewer 证据时必须写“未提供/待核验”，不得根据 `TASKS.md` 的“验收通过”措辞推断 Reviewer 已批准。

已有 T-000、T-001 报告只迁移当前文档中可核实的信息；T-002 及后续任务不提前创建完成报告。

## 5. 正式发布门禁

一个计划版本只有同时满足以下条件，才可由 Release Manager 标记为可发布：

1. 该版本包含的全部任务均有任务报告，且状态与 `TASKS.md` 一致。
2. 每项任务均有明确 Reviewer 通过结论和可追溯证据。
3. 阶段要求的测试已实际执行，报告包含命令、结果和运行日期。
4. `CHANGELOG.md`、任务报告、任务状态和实际工程能力一致。
5. 项目唯一版本号已提升到计划版本，且没有其他项目版本字段冲突。
6. 已知失败和限制被保留，没有把设计目标写成实测结果。
7. 项目所有者明确授权执行发布动作。

任一条件不满足时，版本保持未发布；可记录阻塞项，但不得创建正式版本记录、Git 标签或远程 Release。

## 7. 验证方法

- 检查全部 Markdown 链接和任务—版本映射。
- 搜索项目版本字段，确认 `pyproject.toml` 是唯一声明式项目版本源，并单独报告仍存在的 FastAPI 硬编码风险。
- 解析 `pyproject.toml` 与 `web/package.json`，确认配置语法有效。
- 运行现有静态检查和测试；若环境缺少命令或执行失败，按实际情况报告，不据此虚构通过。
- 核对 `CHANGELOG.md` 不包含未发布版本的虚构日期、测试或 Reviewer 结论。
