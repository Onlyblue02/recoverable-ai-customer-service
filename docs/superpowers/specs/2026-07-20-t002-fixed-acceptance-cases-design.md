# T-002 固定验收用例设计

## 1. 目标与边界

T-002 在任何业务功能实现前，建立后续任务共同遵守的固定验收契约。用例基于 T-001 数据集 `racs-core-business-data` 版本 `1.0.0` 和固定业务基准日 `2026-07-20`，覆盖全部 P0 需求、关键安全边界及两条端到端故事。

本任务只定义用例、Schema 和静态一致性验证，不实现数据库、政策导入或检索、订单 API、资格规则、售后写操作、Agent、工作流、审批、恢复、质量门禁、界面或评测运行器。Schema 和一致性测试通过只证明用例定义有效，不证明未来业务能力已通过这些用例。

## 2. 版本与文件组织

- 用例集名称：`racs-fixed-acceptance-suite`
- 用例集版本：`1.0.0`
- 依赖数据集版本：`1.0.0`
- 固定基准日：`2026-07-20`
- Schema：JSON Schema Draft 2020-12

```text
data/evaluation/
├── README.md
├── manifest.json
├── schema/acceptance-suite.schema.json
├── routing/cases.v1.json
├── retrieval/cases.v1.json
├── rules/cases.v1.json
├── graph/cases.v1.json
├── experience/cases.v1.json
└── e2e/stories.v1.json
```

`manifest.json` 是用例集版本、文件清单、需求覆盖和强制主题覆盖的唯一入口。各模块文件只保存用例，不复制 T-001 实体事实。

## 3. 单个用例结构

每个用例必须包含：

- `case_id`：全局唯一且稳定的 ID，格式为 `AC-FRxx-{N|E|B}-nnn`；端到端故事使用 `E2E-{STANDARD|HIGH_RISK}-nnn`。
- `title`、`case_kind`、`polarity` 和 `requirements`。
- `tags`：标记政策、越权、恢复、安全门禁等强制主题。
- `preconditions`：数据集版本、固定基准日、T-001 fixture 引用及必要的初始状态。
- `user_input`：`semantic_intent`、必须表达的实体或约束、至少两条可互换示例措辞，以及明确的 `semantic_match` 验收方式。
- `expected_process`：有序、可观察的过程步骤；每一步包含事件和必须成立的断言。
- `expected_terminal_state`：单个对象，包含唯一终态 ID、业务状态、公开结果、必须包含/禁止包含内容以及业务副作用计数。

示例措辞只用于说明语义覆盖，不得被未来运行器作为完整字符串相等条件。用例的真正输入契约是意图、实体和约束。

## 4. 覆盖设计

每项 P0 需求至少具有一个 `normal` 用例和一个 `exception` 或 `boundary` 用例。计划覆盖如下：

| 需求 | 正常覆盖 | 异常或边界覆盖 |
| --- | --- | --- |
| FR-01 | 刷新后保留会话与已确认字段 | 等待审批时中断并安全恢复；不兼容状态安全失败 |
| FR-02 | 政策、订单或退货诉求进入正确路径 | 未知诉求两轮无效澄清后升级，且不执行写操作 |
| FR-03 | 当前有效政策回答并引用实际来源 | 过期、无结果、冲突均不生成确定性结论 |
| FR-04 | 当前用户查询自有订单 | 缺少订单号、不存在和越权均得到非泄露结果 |
| FR-05 | 多轮补齐订单号、原因和商品状态 | 用户更正字段后使用最新值，信息不完整时不创建申请 |
| FR-06 | 普通退货得到可重复资格结果 | 质量、7 天边界、8 天超期和高金额得到各自预期或升级 |
| FR-07 | 低风险请求创建唯一模拟申请 | 重复请求返回原结果；失败时禁止成功声明 |
| FR-08 | 人工批准后记录决定并恢复 | 调整、拒绝和重复审批保持一致终态 |
| FR-09 | 有完整依据的回复通过门禁 | 无依据政策、虚假完成状态和审批绕过被阻止 |
| FR-10 | 消费者端展示消息、引用和状态 | 错误可行动且不展示隐藏推理或敏感信息 |
| FR-11 | 审批端展示事实、证据和决定入口 | 已处理审批不可再次提交或改变 |
| FR-12 | 同一固定用例可重复比较结果 | 失败项和限制必须保留，不能包装成成功 |

强制主题至少包括：政策问答、订单查询、越权、退货资格、人工审批、中断恢复、无依据回答、虚假完成状态和审批绕过。

## 5. 两条端到端故事

### 标准退货

使用 `USR-DEMO-001`、`ORD-NORMAL-001` 和 `POL-ACTIVE-STANDARD-001`。期望过程依次包括意图识别、订单归属校验、字段补齐、有效政策证据、确定性资格、低风险判定、唯一模拟申请写入及回复门禁。唯一终态为完成并返回一个有成功操作记录支持的模拟申请结果。

### 高风险人工审批与恢复

使用 `USR-DEMO-001` 和 `ORD-HIGH-VALUE-001`。期望过程包括高金额风险识别、审批快照、`WAITING_APPROVAL` 持久化、中断、从原检查点恢复、人工批准、幂等创建模拟申请及最终门禁。唯一终态为完成且只创建一个申请；重复恢复不得产生第二个申请。

两条故事描述未来可观察行为，不包含当前运行结果或虚构的申请、审批、工作流 ID。

## 6. Schema 与一致性验证

使用开发依赖 `jsonschema` 验证所有用例文件符合 Draft 2020-12 Schema。pytest 进一步验证 JSON Schema 不便表达的跨文件约束：

- manifest 文件清单存在、版本一致且用例 ID 全局唯一；
- FR-01 至 FR-12 均有 normal 和 exception/boundary 覆盖；
- 强制主题和两条端到端故事齐全；
- fixture 引用能解析到 T-001 的用户、订单、商品、政策或售后申请；
- `order_not_found` 只能引用 T-001 清单保留的不存在 ID；
- 越权用例的请求用户与订单所有者不同；
- 政策有效、过期、无结果和冲突引用与 T-001 事实一致；
- 期望过程序号连续，终态对象唯一，副作用计数非负；
- 每个输入至少有两条不同示例措辞，验收方式固定为语义匹配；
- 用例文件不包含 `actual_result`、`passed` 或其他暗示业务已运行的字段。
