# T-202 多轮信息收集与更正设计

## 目标与边界

T-202 在服务端可信上下文中维护退货所需的确认槽位：`order_id`、`return_reason` 和 `item_condition`。它只收集、更新和报告信息，不查询订单、不执行资格规则、不创建申请、不持久化会话，也不实现 T-203 编排。

## 输入与可信边界

- `CollectionRequest` 是公开输入，只含非空用户消息，拒绝额外字段。
- `CollectionContext` 是服务端注入的已确认槽位和修订历史；公开消息不能提交或覆盖该上下文。
- `ReturnInformationCollectionService.collect()` 是唯一公开服务路径，使用有限的订单号和中文关键词模式，不调用任何业务服务。

## 规则与结果

1. 从消息中确定性提取订单号、退货原因和商品状态；“不是旧值，是新值”的受限更正结构优先采用新值，覆盖已声明支持的全部原因和商品状态词表，当前消息提供的新值覆盖同一槽位的旧值。
2. 旧值与新值不同时追加不可变 `SlotRevision`，资格判断后续只能使用最新确认值。
3. 缺失项固定优先级为订单号、退货原因、商品状态；每次结果只给出一个最关键缺失项及对应问题。
4. 三项齐全时返回 `EVALUATING`，表示可由后续 T-203 衔接资格判断；不在本任务调用 T-103 或 T-104。
5. 所有结果固定 `business_operation_requested=false`，因此信息不完整或完整都不会创建售后申请。

## 验证

- 单元测试覆盖多轮补齐、固定缺失优先级、最新值更正与修订历史、公共输入拒绝上下文伪造、空输入。
- 组件测试通过公开路径执行 T-002 的 `AC-FR05-N-001` 与 `AC-FR05-E-001`，验证正常补齐与原因更正。

## 已知限制

识别仅支持明确的合成示例关键词；不保存跨刷新会话状态，不支持自由文本抽取、审批、真实业务操作或工作流编排。可信订单号会去除首尾空白并大写；空字符串或纯空白规范化为缺失订单号并触发单项收集。
