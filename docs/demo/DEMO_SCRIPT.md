# RACS 5–8 分钟演示脚本

## 演示目标

用两条真实公开流程和一个真实失败样本说明：RACS 不只生成对话文本，还把政策证据、订单授权、资格规则、人工审批、恢复与最终回复门禁绑定在一起。

开始前按 [启动指南](STARTUP.md) 启动后端和前端。所有 ID、订单、金额与用户均为固定合成数据。

## 0:00–0:45：问题与边界

讲解：售后机器人必须同时避免过期政策、越权订单、错误资格判断、审批绕过和“未写入却宣称完成”。本项目把这些事实放在确定性服务边界，不交由模型自由决定。

明确：本次是合成演示；没有真实退款、生产认证、数据库持久化或跨进程恢复。消费者与审批页面的主流程当前使用确定性服务组合，不依赖 DeepSeek Key。

## 0:45–3:00：标准退货

在 `http://127.0.0.1:5173` 的消费者对话框依次发送：

```text
我想了解退货政策
我要退货，订单号是 ORD-NORMAL-001
我不想要了
商品未使用，包装完整
```

观察并讲解：

1. 政策问题显示 `POL-ACTIVE-STANDARD-001` 来源。
2. 订单只展示授权白名单字段。
3. 系统逐轮收集原因与商品状态。
4. 只有政策、授权订单、资格与模拟申请成功证据齐全时，页面才显示“已完成”和模拟申请编号。
5. 再次发送“商品未使用，包装完整”，申请编号应保持不变，说明重复保护生效。

可选安全对照：新建会话后输入 `查询订单 ORD-OTHER-USER-001`。页面不显示该订单事实，也不确认订单是否存在。

## 3:00–5:45：高风险审批与恢复

在消费者对话中依次发送：

```text
我要退货，订单号是 ORD-HIGH-VALUE-001
我不想要了
商品未使用，包装完整
```

页面应显示“等待人工审批”。向下滚动至“人工审批工作台”，确认它显示：授权订单摘要、政策 ID/版本/来源、资格结论、命中规则和 `HIGH_VALUE_ORDER` 风险原因。

填写备注“已核验合成订单”，选择“批准”，提交后刷新消费者会话。页面仅在恢复路径已确认模拟申请后显示“已完成”和申请编号。

补充说明：选择“调整”或“拒绝”不会创建申请；重复点击或陈旧版本会由服务端的版本保护拒绝，页面会重新读取可信终态。

## 5:45–7:00：失败案例与质量门禁

打开 [T-403 固定验收报告](../acceptance/T-403-fixed-acceptance-report.md)，展示：

- 10 条代表性公开路径均通过，其中包括检查点导出/导入恢复、无依据回答、虚假完成和审批绕过拦截。
- `T204-T203-GROUNDED-REWRITE-001` 是保留的真实 DeepSeek 合成评测失败：证据 ID 正确，但改写没有命中当时词表的表达。它显示为失败并附改进建议，没有被包装为通过。

可运行以下命令复现报告：

```powershell
.venv\Scripts\python.exe -m customer_service.acceptance_reporting.runner --output reports/evaluations/t403-fixed-acceptance.json
```

## 7:00–8:00：交付结论

总结：标准路径自动完成且可追溯；高风险路径需要人工并能安全恢复；无依据、虚假完成和审批绕过不会被公开放行。最后指出限制：10 条代表性路径不是全部 38 条契约逐条运行；仍需在 v1.0.0 发布前关闭或明确处理联网锁文件与 Docker Compose 验证遗留项。
