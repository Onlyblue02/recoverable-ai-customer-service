## 需求理解与安全边界

T-102 为后续售后判断提供可信订单事实，但不负责退货资格或 Agent 编排。公开查询 payload 只接收订单 ID；当前用户 ID 由服务端独立的 `OrderAccessContext` 注入，不能由订单查询 payload 覆盖。订单是否存在及是否属于该用户由 Mock Business 的可信数据边界判断，不由模型或答案层猜测。

不存在与越权在可信仓库内部保持不同结果，面向非授权调用方则统一为相同状态、错误码、文案和字段集合，避免订单枚举。成功结果只允许输出明确列出的订单和商品字段；下游异常统一安全失败，不公开异常文本。

## 实现

- 固定订单仓库从 T-001 manifest 加载版本为 `1.0.0` 的用户与订单数据，并检查文件声明、数据版本、标识唯一性和订单所有者引用。
- Mock Business API 提供订单查询端点，先查存在性再在仓库边界校验归属；不存在与越权都返回相同 `404/ORDER_UNAVAILABLE` 安全响应。
- HTTP Gateway 同时发送可信上下文中的当前用户 ID 和 payload 中的订单 ID，并将 HTTP、JSON、Schema 与下游合同异常规范化为内部失败。
- HTTP Gateway 对 HTTP 200 响应执行请求绑定：响应 `order_id` 必须与服务实际发送的规范化 `order_id` 完全一致，否则按下游合同失败处理，不公开返回的订单事实。
- 公开 `OrderQueryService.query()` 捕获 Gateway 异常并返回稳定 `ORDER_LOOKUP_UNAVAILABLE`；失败结果的 Schema 禁止携带订单事实。
- T-002 固定用例通过公开路径 `OrderQueryService -> HttpOrderGateway -> Mock Business API -> OrderRepository` 执行，不依赖完全固定的自然语言措辞。

## Reviewer 问题与修复对应

- 可信身份：`OrderQuery` 仅允许 `order_id`，额外身份/授权字段被拒绝；`OrderAccessContext` 独立注入服务端身份。
- 异常安全失败：公开服务捕获下游异常并返回固定 `dependency_failure/ORDER_LOOKUP_UNAVAILABLE`，敏感异常内容不进入序列化结果。
- 枚举信号：不存在与越权公开响应完全一致；仓库内部仍区分 `NOT_FOUND` 与 `UNAUTHORIZED`。
- README：明确“无 HTTP API”的限制只属于 T-101，T-102 的 Mock Business HTTP API 描述保持一致。
- 成功响应串单：HTTP Gateway 在返回 `FOUND` 前严格比较响应与规范化请求 `order_id`；不一致进入现有 `ORDER_LOOKUP_UNAVAILABLE` 脱敏路径，匹配响应保持正常成功。
