# 任务报告规范

## 1. 文件与适用时机

- 每个进入验收的任务使用独立文件 `docs/task-reports/T-xxx.md`。
- 文件名中的任务编号必须与 `TASKS.md` 完全一致。
- 任务尚未进入验收时，不得预先创建带完成结论的报告。
- 报告只记录已发生且可核实的事实；设计目标和计划结果必须明确标注为规划。

## 2. 状态口径

任务报告使用以下状态之一：

- `进行中`：任务尚未完成实现或验证。
- `待 Reviewer`：实现和执行者验证已完成，但缺少 Reviewer 结论。
- `Reviewer 未通过`：Reviewer 已给出阻塞意见。
- `Reviewer 已通过`：存在明确且可追溯的通过结论。
- `已纳入正式版本`：任务已随满足发布门禁的正式版本发布。

如果 `TASKS.md` 使用“验收通过”但没有可追溯 Reviewer 记录，报告必须同时保留该事实，并将发布复核状态标为 `待 Reviewer`，不得自行推断 Reviewer 已通过。

## 3. 必填内容

每份报告必须包含：

1. 任务编号、名称和所属计划版本。
2. 任务目标与范围边界。
3. `TASKS.md` 记录状态和发布复核状态。
4. 实际修改文件或能力；没有证据时明确说明。
5. 实际执行的验证命令、日期和结果。
6. Reviewer 结论、日期和证据位置。
7. 已知限制、失败项和未覆盖风险。
8. Release Manager 的一致性检查与发布资格判断。

## 4. 模板

```markdown
# T-xxx 任务报告

## 基本信息

- 任务：T-xxx 名称
- 所属计划版本：vX.Y.Z
- TASKS.md 状态：进行中 / 验收通过 / 其他原文状态
- 发布复核状态：进行中 / 待 Reviewer / Reviewer 未通过 / Reviewer 已通过 / 已纳入正式版本

## 目标与范围

说明任务目标、实际边界和明确未包含内容。

## 实际修改

只列已经实现并能由文件、提交或运行结果证明的内容。

## 验证记录

- 执行日期：YYYY-MM-DD
- 命令：`实际执行命令`
- 实际结果：通过数量、失败数量、错误或未执行原因
- 证据：日志、CI、提交或其他可追溯位置

## Reviewer 结论

- 结论：通过 / 未通过 / 未提供、待核验
- 日期：YYYY-MM-DD / 未提供
- 证据：链接、文件或记录位置 / 未提供

## 已知限制与风险

保留失败、未覆盖范围和后续依赖。

## 发布资格

- 判断：满足 / 不满足
- 原因：逐项说明发布门禁满足情况或阻塞项
```

## 5. 维护规则

- 新测试结果追加执行日期和实际结果，不覆盖重要历史失败。
- Reviewer 结论变化时保留原结论摘要，并记录新结论及证据。
- 任务报告不得代替 `CHANGELOG.md`；前者记录任务证据，后者记录版本变化。
- 正式发布后才可将状态改为 `已纳入正式版本`。
