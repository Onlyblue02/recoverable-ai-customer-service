## 审核项关闭记录

1. `ValidatedToolStep` 不再是执行授权：校验器内部签发一次性许可，公开只暴露无签发方法且受构造令牌保护的消费视图。许可绑定会话、回合、用户、状态和步骤；伪造、错绑定、新建 authority 与重放均拒绝。后续写入/高风险动作由执行器私有 continuation authority 签发，模型不能签发。
2. 成功的订单、政策、资格、审批、高风险启动/恢复和申请结果由同一受控执行路径登记回执并签发绑定的 `EvidenceRecord`。失败、越权、超时和未知写入不签发公开证据；伪造回执仍无法通过 T-604 authority。
3. `policy.lookup` 从服务端 `PolicyContextProvider` 取得绑定会话/回合/用户的查询上下文并实际执行。`approval.get_status` 已进入固定 ToolId/合同；低风险创建、高风险启动、审批状态与恢复都只消费执行器签发的一次性 continuation permit。高风险复用 T-301/T-302/T-304；新审批若检查点失败会仅补偿删除本次仍 pending 的任务，不留下孤立审批。
4. 低风险申请仅由本回合实际 `eligible` 结果签发 `service_case.create` continuation，绑定已授权订单、商品行、用户、资格和稳定幂等键。错用户/会话/状态、非 eligible 和重放不能写入；下游写入异常沿用既有安全失败和未知状态规则。
5. 生产 `InMemoryEvidenceAuthority` 已移除 `_issue_for_controlled_execution` 等直接签发入口；受控回执创建能力仅由 `ControlledToolExecutor` 内部闭包持有，authority 的公开消费入口无法用伪造订单、商品行、资格、审批或申请回执签发记录。
6. `agent_runtime` 包初始化改为延迟兼容导出，切断 `agent_runtime.__init__ → executor → evidence → schemas → agent_runtime` 循环，同时保留 T-602 的包级导入行为；四个相关模块及原包级导出均由全新 Python 进程独立导入测试覆盖。
7. `return.evaluate` 的内部结果现在携带授权订单实际商品行，并将 `order_id`、`order_item_id`、资格结论、政策 ID 和政策版本共同写入 EvidenceRecord；商品行只来自订单服务，模型、permit 和调用方不能提供。错误商品行的 EvidenceBinding 被拒绝，订单及政策查询不会伪造商品行，低风险和高风险 continuation 均沿用同一受控商品行。

以上第 1～4 项分别对应 Reviewer 的四项阻塞及其关闭证据；第 5～7 项是关闭过程中补充的签发入口收紧、导入边界和商品行绑定回归证据。
